# Référence — Fonctions SECURITY DEFINER et Realtime SQL

> La table complète des RPC du projet. À consulter avant d'en écrire une nouvelle : la moitié des chantiers récents ont découvert qu'une fonction existante couvrait déjà le besoin.

> ⚠️ **Rappel du cœur de `CLAUDE.md`, qui prime sur ce document** : la vérité est **en base**, pas ici. Avant de réécrire une fonction, lire sa définition courante avec `pg_get_functiondef` — cette table est tenue à la main et peut avoir pris du retard sur la base.

## Fonctions SECURITY DEFINER

| Fonction | Rôle |
|---|---|
| `is_table_participant(uuid)` | Helper RLS anti-récursion |
| `is_table_moderator(uuid)` | **Chantier 60** — helper d'autorité d'animation, anti-récursion (`SECURITY DEFINER STABLE`, `search_path = public, extensions`). Vrai si l'appelant est le **créateur** de la table (`tables.created_by`) **ou** un membre de la séance marqué `session_members.is_moderator` **et** affecté à **cette table précise** (`table_assignments`) — les deux conditions de la 2ᵉ branche sont cumulatives. Utilisé par `grant_floor`, `end_turn`, `end_turn_and_advance`, `kick_participant`, `add_offline_participant`, `add_to_queue`, `move_queue_entry`, `reorder_queue_entry`, `correct_turn`, et par 6 policies RLS (`tables_update_moderator`, `queue_entries_*`, `speaking_turns_*`). **Ne jamais réintroduire un test direct `created_by = auth.uid()` dans une garde d'animation** : `apply_allocation`/`create_tables_batch` posent `created_by` = l'uid du **superadmin**, pas celui du modérateur assis. **Chantier 54** : `tables_delete_moderator` (posée par le chantier 60 sur ce même helper) a été **supprimée sans remplacement** — un modérateur ne doit plus jamais pouvoir supprimer sa table, y compris par appel direct à l'API REST (le bouton correspondant, `endTable()`, avait déjà été retiré de l'UI en juin 2026, mais la policy RLS restait active). Seul le superadmin peut encore supprimer une table, via la RPC `SECURITY DEFINER` `delete_table_admin` (indépendante de cette policy) |
| `is_own_session_member(uuid)` | **Chantier 50** — helper RLS anti-récursion pour `table_assignments` (`SECURITY DEFINER STABLE`, `search_path = public, extensions`). Vrai si la ligne `session_members` visée appartient à l'appelant. Nécessaire parce que la policy de `table_assignments` doit lire `session_members`, elle-même sous RLS |

Reste le seul chemin de VRAIE reprise de main par quelqu'un déjà modérateur de cette table, mais n'est plus appelée par aucun écran (`JoinTableForm`/`EntryScreen` sont passés à `claim_table_as_moderator` — voir A_VERIFIER.md, chantier 68, pour le point resté ouvert sur l'absence de chemin UI dédié à la vraie reprise de main) |
| `table_has_moderator(table_id)` | **Chantier 68** — `SECURITY DEFINER STABLE`, `search_path = public, extensions`. Généralisation de `is_table_moderator` : répond « quelqu'un a-t-il déjà autorité sur cette table ? » (pas « l'appelant en a-t-il ? », inutilisable pour un nouvel arrivant sans historique). Vrai si la table n'est pas `leaderless` et son créateur y est physiquement assis, ou si un modérateur Bloc C désigné (`session_members.is_moderator` + `table_assignments`) y est assis |
| `claim_table_as_moderator(join_code, creation_code, pseudo, session_id?)` | **Chantier 68** — un modérateur en retard prend en charge une table par son code, refusée si le Code Ecclesia est invalide, si `session_id` (optionnel) ne correspond pas à la séance de cette table, ou si `table_has_moderator` répond vrai. Cible aussi les tables `leaderless` (aucun modérateur par construction) et pose `leaderless = false` sur succès, comme le chantier 64 |

| `assign_moderator_to_table(password, session_id, table_number, member_id)` | **Chantier 33 (point 2)** — assigne manuellement un membre comme modérateur d'une table précise (glisser-déposer ou saisie de nom, onglet Groupes). Pose `is_moderator=true` et (dé)place la ligne `table_assignments` en une transaction. **Chantier 64** : si la table physique visée par `table_number` est `leaderless`, elle est convertie (`leaderless = false`) dans la même transaction. |
| `switch_table(session_id, join_code, pseudo)` | **Chantier 48** — un participant rejoint une AUTRE table que celle assignée (`AllocatingScreen`, saisie du code à 6 caractères). Vérifie que le code appartient à la séance, retire proprement le participant de sa/ses table(s) précédente(s) (clôt le tour en cours si besoin, cascade `queue_entries`), insère la nouvelle ligne `participants`, déplace `table_assignments` via `sync_table_assignment`. **Chantier 64 (complément)** : si l'appelant était le modérateur Bloc C (`session_members.is_moderator`) de la table quittée, celle-ci redevient `leaderless = true` — mais seulement si `leaderless_by_design = true` (convertie depuis une table sans modérateur) ; une table conçue modérée dès l'origine (`leaderless_by_design = false`) ne bascule jamais, quel que soit le départ. | `move_member_to_group(password, session_id, member_id, target_table_number)` | Glisser-déposer d'un membre vers un autre groupe (onglet Groupes, superadmin) — déplace sa ligne `table_assignments` (`table_number`/`table_id`), rien d'autre (ne touche jamais `participants` : le rejoint physique reste séparé). **Chantier 64 (complément 2)** : même bascule que `switch_table` — si le membre déplacé était le modérateur Bloc C de la table quittée et qu'elle est `leaderless_by_design = true`, elle redevient `leaderless = true`. Deux chemins désormais couverts par la même règle ; voir l'en-tête de `20260902_chantier64c_move_member_to_group_revert.sql` pour l'inventaire complet des chemins qui retirent un membre d'une table (et ceux volontairement exclus : `set_member_moderator(false)` en place, `kick_participant` sans destination, `assign_table_to_group` qui rebind tout un groupe et non un membre). |

**RLS Realtime** : `REPLICA IDENTITY FULL` sur les tables suivantes — obligatoire pour que les événements filtrés (DELETE et UPDATE avec RLS) arrivent aux subscribers :
- `tables`, `participants`, `queue_entries`, `speaking_turns` (migration `core_functions`)
- `table_assignments` (migration `20260530`) : sans ça, un UPDATE de `table_id` seul ne transmet pas `session_id` dans le WAL → le filtre Realtime `session_id=eq.<id>` ne peut pas matcher
- `sessions` (migration `20260615`) : sans ça, les UPDATE de phase (draft→voting, allocating→debating) ne sont pas livrés aux participants → les transitions de phase nécessitaient un reload manuel

Les tables Bloc C (`session_members`, `assertions`, `assertion_votes`, `table_assignments`) sont dans la publication Realtime — pas de broadcast custom, Realtime natif uniquement.
